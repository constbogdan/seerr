# TMDB movie collection membership observations

The `movie_collection_observation` table stores global, typed TMDB movie metadata, not user Watchlist ownership, requests, or evidence of physical library presence. A row with a positive `tmdbCollectionId` confirms a collection; a row with a null ID confirms a standalone movie. No row means unresolved. The observation timestamp is retained separately from the membership state. Newer confirmed observations win; equal timestamps prefer an existing canonical observation. Stale confirmed values remain available if refresh fails.

Fresh identity verification and explicit Watchlist additions record membership from movie details they already fetch. They do not crawl old rows. Recommendation enrichment is off by default. `includeCollectionIds=true` admits at most four movie-detail fallbacks per page, four at a time, with a one-second admission deadline; already-started provider calls are awaited and retain the existing TMDB transport timeout. This is not a hard response deadline: contention in the shared provider queue may make an opt-in response take longer. Partially resolved pages are expected. The provider's existing concurrency limiter also applies.

The SQLite and PostgreSQL migrations are additive. They do not backfill history or create CanonicalMedia rows. Before rolling back, back up `movie_collection_observation` if its observations should be retained: the down migration drops that table and therefore deletes its data. Do not mark unknown movies as standalone or modify canonical/library checkpoints to compensate. A later deployment can repopulate observations incrementally from normal usage.
